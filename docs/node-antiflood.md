# Абуза хостера «флуд/DDoS с вашего сервера»

Разбор инцидента на **node-pl-1** (203.0.113.30), 12.09.2026: хостер
зафиксировал 106 170 исходящих пакетов/с, остановил сервер и выдал
предупреждение 2 из 3. Третье — удаление сервера и блокировка аккаунта.

## Что нашли

Источник — аккаунт `user_<TG_ID>` (в боте это `heavy_user`, ваш личный):

| Параметр | Значение | Норма по парку |
|---|---|---|
| Трафик за 15 дней | **25.2 ТБ** | следующий по объёму — 2.8 ТБ |
| На node-pl-1 | 200–350 ГБ **в сутки**, каждый день | 15–25 ГБ/сутки |
| `hwid_device_limit` | не задан → **628 устройств** | — |
| `traffic_limit_bytes` | 100 ТБ/мес | 1 ТБ/мес у всех остальных |
| `expire_at` | 2036 год | — |

Ключ разошёлся по 628 устройствам, и кто-то из них гоняет торрент-раздачу
либо стресс-тест. 350 ГБ/сутки мелкими UDP-пакетами — это и есть те 106к pps.

Важно: через VPN-ноду **невозможна классическая амплификация со спуфингом** —
source IP подделать нельзя, ответ всё равно вернётся на ноду. Значит это был
прямой флуд (или торрент-DHT), и защищаться надо не блок-листом портов
амплификации, а потолком pps.

## Почему конфиг ноды это пропустил

`NodePlConfig` имел в `routing` всего два правила: `geoip:private` → BLOCK и
`protocol: bittorrent` → BLOCK. Три дыры:

1. **HY2-инбаунд был без `sniffing`.** Правило `protocol: bittorrent`
   срабатывает только от сниффера. У `NODE-PL-HY2` секции `sniffing` не было
   вообще → весь трафик через Hysteria2 уходил в `DIRECT` без единой проверки.
   То же самое было на **всех** нодах с HY2: de-2, nl-2, ru-2, es-1.
2. **Детект bittorrent дырявый по своей природе.** Xray опознаёт BitTorrent
   по TCP-хендшейку; DHT и uTP идут по UDP и как `bittorrent` не опознаются
   никогда — даже там, где сниффинг включён.
3. **Ни одного ограничения по портам и сети.** Наружу можно было слать любой
   UDP на любой порт в любом объёме.

## Что сделано

### 1. Routing в Config Profile

Скрипт [`scripts/remnawave_antiflood_routing.py`](../scripts/remnawave_antiflood_routing.py)
(лежит на panel-server как `/root/antiflood.py`, ходит в панель через `rwapi.py`):

```bash
python3 /root/antiflood.py NodePlConfig          # dry run
python3 /root/antiflood.py NodePlConfig --apply  # записать + проверить
```

Бэкап прежнего конфига уходит в `/root/rw-backups/<Профиль>_<таймштамп>.json`.
Откат — `PATCH /api/config-profiles` с содержимым бэкапа.

Ставит 9 правил; ключевые два — жёсткий **whitelist UDP**:

```jsonc
{ "ruleTag": "UDP_ALLOW",     "network": "udp",
  "port": "53,443,3478,19302-19309", "outboundTag": "DIRECT" },
{ "ruleTag": "UDP_DENY_REST", "network": "udp", "outboundTag": "BLOCK" }
```

Xray не понимает отрицание в `port`, поэтому whitelist делается порядком
правил: сначала разрешающее, следом запрещающее всё остальное.

Эти два правила матчатся по `network`/`port`, а **не** по результату сниффера —
поэтому работают и на HY2, и на любом инбаунде без `sniffing`. Это и есть
главная причина выбрать порт-матчинг вместо протокольного.

Заодно скрипт включает `sniffing` на HY2-инбаундах и ставит
`domainStrategy: IPIfNonMatch` (без него правила с `ip:` не применяются к
запросам, пришедшим доменом — то есть `geoip:private` раньше мог не срабатывать).

**Что ломается whitelist'ом:** звонки Telegram/WhatsApp (ходят на произвольные
UDP-порты), онлайн-игры, WireGuard/OpenVPN внутри туннеля. HTTP/3 и DNS живут
(443 и 53 разрешены). Если жалобы на звонки перевесят — убрать правило
`UDP_DENY_REST`, тогда останется блок-лист `ABUSE_UDP_AMPLIFICATION` плюс
потолок pps из следующего пункта.

### 2. Потолок pps в ядре ноды

**Xray не умеет ограничивать пакеты в секунду** — он умеет только запрещать
классы трафика. Гарантию «больше 106к не выйдет» даёт только фаервол:

```bash
scp scripts/node_antiflood_firewall.sh node-pl-1:/root/
ssh node-pl-1 '/root/node_antiflood_firewall.sh install'
```

| Лимит | Значение | Почему столько |
|---|---|---|
| UDP на одну цель | 3000 pps | хватает видеозвонку и игре |
| UDP суммарно | 25 000 pps | ловит флуд веером по многим целям |
| TCP SYN на цель | 300 pps | лимитируем только новые соединения |
| Всё исходящее | 80 000 pps | аварийный потолок ниже 106к |

TCP-поток намеренно **не** лимитируется по pps: при скачивании на 200 Мбит/с
исходящих ACK'ов около 8к pps на один адрес, и общий лимит порезал бы скорость.

Проверка после инцидента — `./node_antiflood_firewall.sh status`, ненулевой
`pkts` в строках DROP означает, что флуд поймали.

### 3. Аккаунт-виновник

Правки конфига не мешают одному ключу на 628 устройств качать легальный
трафик терабайтами. Отдельно нужно:

- поставить `hwid_device_limit` (3–5) на `user_<TG_ID>`;
- сбросить его `traffic_limit_bytes` со 100 ТБ до вменяемого;
- перевыпустить подписку (`sub_revoked_at`), чтобы отсечь разошедшийся ключ.

Лимит устройств можно ставить безопасно: экран «Мои устройства» уже есть в боте
(`/devices`), на сайте и в Mini App — упёршийся в лимит пользователь освобождает
слот сам, не обращаясь в поддержку. См. `tgbot/services/device_service.py`.

## Профилактика

Раз в неделю смотреть перекос по трафику — аномалия видна сразу:

```sql
SELECT u.username, round(sum(h.total_bytes)/1099511627776.0,2) AS tb,
       u.hwid_device_limit
FROM nodes_user_usage_history h JOIN users u ON u.t_id = h.user_id
WHERE h.created_at > current_date - 7
GROUP BY 1,3 ORDER BY 2 DESC LIMIT 10;
```

Запускать на panel-server: `docker exec remnawave-db psql -U postgres -d postgres`.
